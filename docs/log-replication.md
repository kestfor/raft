# Журнал и репликация

Узел принимает команды через `Node.Propose(ctx, data)` или gRPC `Propose`.
Лидер сначала сохраняет команду локально, затем реплицирует её. Успешный ответ
означает commit большинством, а не выполнение команды state machine.
State machine, дедупликация клиентских запросов, snapshots и компакция пока не реализованы.

## Использование

Для каждого узла нужен отдельный `data_dir` (`RAFT_DATA_DIR`, `--data-dir`).
В локальных конфигурациях это `data/node1`, `data/node2`, `data/node3`;
Docker Compose использует отдельные named volumes. Перезапуск сохраняет журнал.
`docker compose down -v` удаляет данные вместе с volumes.

Запустить три узла в отдельных терминалах:

```sh
go run ./cmd/raftnode --config=configs/local/node1.yaml
go run ./cmd/raftnode --config=configs/local/node2.yaml
go run ./cmd/raftnode --config=configs/local/node3.yaml
```

Найти лидера через `GetStatus` и отправить ему команду (поле bytes в JSON — base64):

```sh
grpcurl -plaintext localhost:19001 raft.v1.RaftService/GetStatus
grpcurl -plaintext -max-time 5 -d '{"data":"aGVsbG8="}' localhost:19001 raft.v1.RaftService/Propose
```

Если лидер на другом порту, заменить адрес. `GetStatus` возвращает `last_log_index`
и `commit_index`. В индексы входят служебные no-op записи, поэтому первая команда
не обязательно имеет индекс 1. Follower возвращает `FailedPrecondition` на Propose;
автоматического перенаправления нет.

При отмене контекста, потере лидерства или ошибке диска результат команды может
остаться неизвестным: запись могла сохраниться и позже попасть в commit.
Go API возвращает индекс после успешной локальной записи даже при ошибке ожидания;
gRPC при ошибке не возвращает индекс. Нулевой индекс при ошибке записи не доказывает,
что запись отсутствует на диске. Повторная отправка создаёт новую запись.

## Хранение

`pkg/wal` не знает о Raft. Он хранит непрозрачные записи в одном файле `raft.wal`
и предоставляет `Open`, `Append`, `Replay`, `Close`. `Append` включает `fsync`.
Формат: заголовок `RAFTWAL1`, далее записи с длиной uint32, CRC32 длины, CRC32
данных и самими данными. Числа записаны в little endian; максимум записи — 16 MiB.
CRC длины позволяет отличить повреждённую длину от незавершённого тела записи.
При открытии неполный последний заголовок или тело отбрасывается; неверная checksum
вызывает ошибку открытия. Повреждённые полные записи автоматически не исправляются.
Перед успешным открытием восстановленный файл синхронизируется: полная запись
могла остаться в кеше ОС после падения процесса до завершения fsync.
Файл блокируется через Unix flock на весь срок открытия; поддерживаются macOS/Linux.

`pkg/raft` кодирует одну операцию хранения в JSON: ID узла, текущий term, votedFor
и необязательный новый хвост лога. При replay хвост заменяет записи начиная со своего
первого индекса. Замена целиком помещается в одну запись WAL. Старые версии хвоста
физически остаются в WAL: размер файла и время восстановления растут.
Сам Raft-лог целиком находится в памяти. Это осознанные ограничения этой итерации.

Изменения публикуются в памяти после успешного Append. Ошибка хранения прекращает
участие узла в протоколе и возвращается из Run; дальнейшие записи в этот WAL запрещены
до закрытия и повторного открытия. Гарантии долговечности зависят от файловой системы
и соблюдения устройством fsync. Не следует использовать сетевые файловые системы.

Storage передаётся через `raft.Config.Storage`; его открывает и закрывает вызывающий
код. Закрывать нужно после завершения Run и вызовов узла. `nil` означает режим
только в памяти для тестов; CLI всегда использует WAL. NewNode восстанавливает
журнал и hard state до запуска RPC. Файл другого ID узла не принимается.

## Правила Raft

- AppendEntries проверяет `prevLogIndex`/`prevLogTerm`, включая heartbeat.
  Совпадающие записи не переписываются; при первом конфликте заменяется хвост.
  Пустой или повторный запрос не удаляет совпадающий хвост.
- Follower продвигает commit только до минимума `leaderCommit` и последнего индекса,
  подтверждённого конкретным запросом. Известные committed-записи не заменяются.
- RequestVote сравнивает term последней записи кандидата, затем её индекс.
  Term и голос сохраняются до отправки RPC/ответа; один голос переживает рестарт.
- Лидер хранит nextIndex/matchIndex отдельно для каждого peer. Одновременно идёт
  не более одного RPC на peer. Конфликт уменьшает nextIndex на один, успешный ответ
  продвигает matchIndex; устаревшие ответы не меняют прогресс нового лидерства.
- Commit большинством вычисляется только для записи текущего term. При избрании
  лидер добавляет no-op, позволяющий подтвердить также записи прошлых термов.
- CommitIndex — volatile state, при рестарте начинается с нуля и восстанавливается
  из общения с лидером либо через commit no-op после собственного избрания.
- Команда ограничена 1 MiB; AppendEntries — 64 записи и 1 MiB суммарных данных.
  Следующие пакеты отправляются после ответа, heartbeat обеспечивает повтор при ошибке.

Не поддерживается смешанный кластер со старой реализацией heartbeat-only: её узлы
не проверяют актуальность логов и не сохраняют записи.

## Проверка

`make test` запускает тесты с race detector, `make lint` — линтер,
`make proto` — проверку и генерацию protobuf. Тесты покрывают конфликты и повторную
доставку, ограничения commit, смену лидера и восстановление разделённого кластера,
голосование с непустым логом, восстановление WAL, неполные записи и ошибки хранения.
