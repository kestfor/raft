# State machine

`raft.StateMachine` выполняет прикладные команды из committed-части журнала:

```go
type StateMachine interface {
    Do(entry Entry) (any, error)
}
```

Передайте реализацию через `raft.Config.StateMachine`. Если поле не заполнено,
`NewNode` подключает `raft.NoOpStateMachine`: она ничего не меняет и возвращает
`nil, nil`. Для KV-хранилища достаточно заменить её собственной реализацией,
которая декодирует `entry.Data` и изменяет локальное хранилище.

```go
cfg := raft.DefaultConfig(id, peers)
cfg.StateMachine = store // store реализует Do(raft.Entry) (any, error).
node, err := raft.NewNode(cfg, transport)
// Запустить node.Run(ctx) перед отправкой команд.
index, result, err := node.Propose(ctx, command)
```

## Применение и результат

Один цикл внутри `Run` последовательно обрабатывает записи от `lastApplied + 1`
до `commitIndex` на каждом узле независимо от его текущей роли. Лидер продвигает
commit после подтверждения большинства, follower узнаёт его из `AppendEntries`.
Оба пути уже уведомляют цикл через `log.changed`.

`Do` получает копию `Entry`, включая отдельную копию `Data`, и выполняется вне
mutex Raft. Служебные `NoOp` не передаются в `Do`, но продвигают applied index.
`Node.Status().AppliedIndex` обновляется после завершения применения записи.

`Propose(ctx, data) (index uint64, result any, err error)` возвращает успех после
commit и локального применения команды. Результат относится к конкретной записи.
Потеря лидерства после commit не мешает дождаться её применения. Результаты
хранятся только для ожидающих запросов, а не для всего журнала.

В KV-сервере `Store` реализует `Do`, а `POST /query` подтверждает применение
индексом записи. Формат клиентского API задан в `api/client_openapi.json`.

## Контракт реализации

- На каждом узле нужен отдельный экземпляр state machine с одинаковой логикой.
- Применение должно быть детерминированным: одна последовательность команд даёт
  одинаковое состояние и результаты. Время и случайность передаются в команде,
  если они нужны прикладной логике.
- Возвращённый результат должен оставаться неизменным после следующих вызовов
  `Do`. Например, при возврате значений из map нужно копировать изменяемые данные.
- Ошибка `Do` считается фатальной: узел прекращает участие в протоколе, `Run`
  и ожидающие запросы получают ошибку. Ожидаемые прикладные отказы передаются
  в `result`, например структурой с кодом отказа.
- `Do` должен завершаться за ограниченное время. При остановке `Run` дожидается
  текущего вызова; новые команды после остановки не запускаются. Синхронно
  ожидать другой `Propose` на том же узле из `Do` нельзя.
- Отмена клиентского контекста прекращает ожидание результата и не отменяет
  committed-команду. Автоматической дедупликации повторных запросов нет.

## Восстановление

После рестарта state machine должна быть пустой. При подключении дискового WAL он восстанавливает журнал,
а записи применяются заново после подтверждения commit. Новый лидер уже пишет
`NoOp` своего term, что позволяет подтвердить и восстановленный префикс.

Хранилище со своим сохранённым состоянием пока не поддерживается: для него нужно
согласованно восстанавливать состояние и applied index, например через snapshots.

## Сверка с Raft

Реализация следует [статье из репозитория](raft.pdf):

- §2: детерминированное выполнение одной последовательности команд на всех узлах.
- Figure 2, §5.3 и §5.4.3: применение только committed-записей по индексам;
  ответ клиенту после применения; одинаковое правило для всех ролей.
- §7: состояние snapshot и индекс последней применённой записи восстанавливаются
  совместно. До поддержки snapshots используется пустое состояние и replay.
- §8: дедупликация по идентификаторам клиентских запросов относится к state
  machine. Без неё повторный запрос может исполниться повторно.

Линейризуемый GET в KV использует `ReadIndex`: подтверждение лидерства
большинством и ожидание применения нужного commit index согласно §8.
